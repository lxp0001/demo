# 阶段六教师用:练习系统设置与评分说明(不发给学生)

## 一、结构混乱版本的设置
在第五阶段的订单系统基础上,制造以下架构问题(保持功能和第四阶段的测试可通过,即行为不变):
| 编号 | 问题 | 影响的质量属性 |
|---|---|---|
| X1 | 接口层直接写 SQL 并创建数据库连接 | 可修改性、可测试性 |
| X2 | 业务规则散落在接口函数和数据访问函数中(如总价计算出现在两处) | 可修改性 |
| X3 | 业务层和接口层直接导入支付客户端的具体实现,没有抽象,无法替换 | 可修改性、可测试性 |
| X4 | 数据库路径、支付地址、密钥写死在代码里 | 可部署性 |
| X5 | 订单业务与数据访问之间存在循环依赖 | 可修改性 |
| X6 | 使用全局可变状态(全局数据库连接),导致测试之间互相影响 | 可测试性 |

另提供:
- 一个**正确的参考架构版本**,用于验证学生的重构没有改变行为。
- 第四阶段的**全部测试**,作为重构的安全网。
- 一个简单的 **`GET /health`** 的约定(返回 200)。

## 二、变更演练(隐藏)
事先不告知学生,在重构完成后给出。可选的变更:
- 把支付换成另一种实现(检验外部服务是否通过抽象接入)。
- 切换数据库到 MySQL(检验配置外部化和数据访问是否隔离)。
- 新增一个订单状态或一个字段(检验业务规则是否集中)。
评分看**改动范围**:改动的文件数和行数,以及测试是否仍然通过。

## 三、评分建议
- **自动检查**:全部测试通过;依赖规则脚本无违规(检查导入方向);在**新克隆的仓库**里按学生 README 里的命令启动,并访问 `GET /health` 返回 200。
- **变更演练**:按改动范围和测试结果评分。
- **AI 评价**:问题清单是否有证据、决策是否写了备选方案和代价、重构计划是否在使用 Agent 之前完成。
- **人工评价**:现场解释一个决策的取舍。
- 学生提出的、不在上表中的合理架构问题,经确认后同样给分。

## 四、还需要准备的内容
- 结构混乱版本和参考版本的代码。
- 依赖规则检查脚本(可检查导入方向)。
- 干净克隆启动和 `/health` 的检查脚本。
- 隐藏的变更需求及其评分阈值。
- Windows 上命令启动请统一使用 Git Bash 编写和检查命令。
- Docker Compose 配置模板(仅供选做的学生参考)。
