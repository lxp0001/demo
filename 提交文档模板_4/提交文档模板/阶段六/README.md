# 第六阶段｜软件架构：食堂订单系统

本阶段在前五个阶段的食堂订单系统上继续。老师提供一个“能用但结构混乱”的订单系统，学生要从代码还原现状架构，论证改进方案，再小步、安全地重构，最后通过一次事先不告知的变更来检验架构改造的效果。本阶段不要求推倒重写，难度与第四、五阶段相当。

| 任务 | 学习重点 | 本任务完成时能看到什么 |
|---|---|---|
| 6.1 架构分析与决策记录 | 还原依赖图、架构问题、质量属性、备选方案与代价 | 现状依赖图、问题清单、架构决策记录 |
| 6.2 架构改造与可重复启动 | 小步重构、依赖规则、配置外部化、命令启动、变更演练 | 重构后的代码、依赖规则检查、干净环境启动记录、变更演练记录 |

## 学生完成方式

每项任务保留“独立草案 → Agent 评审与回应 → 运行证据 → 人工判断与修订”。本阶段有三条硬要求：

- **先理解，再改动**：没有还原现状依赖图，不能开始重构。
- **小步重构**：每一步之后都要运行第四阶段的全部测试，行为不变才能继续；失败就回退。
- **每个决策写明备选方案和代价**：不接受“这样更好”这样的说法。

Agent 可以评审依赖图和重构步骤，但依赖图要由学生自己画，重构方案要由学生自己决定。

## 范围说明

- 只做订单系统的后端，以及必要的启动配置。
- 项目必须支持用命令启动：在干净的环境中，按 README 里写明的命令就能启动，并且 `GET /health` 返回 200。
- Docker Compose 一键启动为**选做**，不作为必做要求。
- 不做微服务拆分、消息队列和云部署。
