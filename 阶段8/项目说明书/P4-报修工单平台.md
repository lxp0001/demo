# P4 报修工单平台

- 难度:B 到 C
- 典型需求方:物业、写字楼、公寓管理方

## 背景
住户报修,管理员派单,维修人员处理,住户评价。需要有状态流转、超时升级和通知。

## 用户与角色
- 住户:提交报修、查看自己的工单、评价。
- 管理员:查看所有工单、派单、处理超时。
- 维修人员:查看分配给自己的工单并更新状态。

## 增量里程碑
- **M1**:报修与工单状态,可命令启动,有健康检查和 CI。
- **M2**:派单与角色权限。
- **M3**:超时升级(定时)。
- **M4**:通知(模拟)、评价与审计日志。

## 非平凡逻辑(用「一句话需求能否直接生成正确答案」来检验)
工单状态流转的合法性校验,以及超时升级的规则(多久升级、升级给谁、已处理的工单如何排除)。

## 主要难点
- 多角色权限(住户只能看自己的工单)。
- 状态机的合法转换。
- 定时任务的可靠性与幂等。
- 重复报修的合并。

## 需要向需求方澄清的问题
1. 超时的标准是多久?升级给谁?
2. 重复报修如何识别与合并?
3. 哪些工单属于紧急,处理流程有什么不同?
4. 住户的哪些信息维修人员可以看到?
5. 评价是否影响派单?

> 备注:如果项目进展顺利,可以在 P4 的基础上增加「工单智能分类与摘要」作为选做,AI 类要求见 P8。

## 数据与保密提示
- 只收集完成功能所必需的信息;开发和测试使用脱敏的假数据。
- 使用外部 Agent 或模型服务前,先确认需求方是否允许把代码或数据交给外部服务。
- 不提交密钥和真实个人数据;不直接操作需求方的生产环境数据。

## 评价关注点
- 需求是否经过需求方确认,假设是否被验证。
- 设计是否在实现之前,测试是否先行。
- 变更是否有影响分析。
- 质量证据:测试、依赖规则、安全检查、性能基线、命令启动。
