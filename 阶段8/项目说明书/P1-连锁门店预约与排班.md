# P1 连锁门店预约与排班

- 难度:C(挑战档,设计评审后确认)
- 典型需求方:小型连锁商户(理发、健身、培训等)

## 背景
多家门店、多名员工,顾客按门店、服务和员工预约。门店需要管理排班,并在员工请假、临时调班时处理已有预约。

## 用户与角色
- 顾客:查看可预约时段,预约、取消。
- 员工:查看自己的排班和预约。
- 店长:管理本门店的员工、排班和预约。
- 总部管理员:跨门店查看,不能随意修改门店数据。

## 增量里程碑
- **M1**:单店预约与冲突检测,可命令启动,有健康检查和 CI。
- **M2**:员工排班与预约联动。
- **M3**:多门店数据隔离与权限矩阵。
- **M4**:候补、通知(模拟)与审计日志。

## 非平凡逻辑(用「一句话需求能否直接生成正确答案」来检验)
可预约时段的计算:综合服务时长、员工排班、已有预约和门店营业时间;排班变动时对已有预约的处理规则。

## 主要难点
- 门店之间的数据隔离和权限矩阵。
- 排班变动与已有预约的联动。
- 并发抢同一时段。
- 审计日志:谁在什么时候改了什么。

## 需要向需求方澄清的问题
1. 员工请假后,已预约的顾客怎么处理?
2. 一次预约会占几个时段?不同服务时长如何计算?
3. 不同门店的服务和价格是否一致?
4. 店长和总部管理员的权限差别是什么?
5. 候补的规则是什么?

## 数据与保密提示
- 只收集完成功能所必需的信息;开发和测试使用脱敏的假数据。
- 使用外部 Agent 或模型服务前,先确认需求方是否允许把代码或数据交给外部服务。
- 不提交密钥和真实个人数据;不直接操作需求方的生产环境数据。

## 评价关注点
- 需求是否经过需求方确认,假设是否被验证。
- 设计是否在实现之前,测试是否先行。
- 变更是否有影响分析。
- 质量证据:测试、依赖规则、安全检查、性能基线、命令启动。
