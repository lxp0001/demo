# 阶段七填写示例｜食堂订单系统

示例展示填写方法，尤其是如何用数据而不是感觉做比较，以及如何记录审查和授权的理由。示例中的数字和问题只用于展示写法。请用自己运行项目得到的结果替换示例。

## 任务 7.1：任务拆解与规格说明

- 我的拆解（菜品搜索与分页）：①定义查询参数；②实现按名称搜索；③实现分页；④处理边界（页码为 0、超出范围、每页数量过大）；⑤补充测试。每个小任务都写了完成标准和验证方式。
- 我的规格：页码从 1 开始；每页数量默认 10、最大 50；搜索词使用参数化查询。
- 项目约定文件里的一条规则：不修改已有测试的断言；新增依赖要先说明理由。
- 对照实验（同一功能，两种方式）：

| 指标 | 一句话直接交给 Agent | 先拆解规格再分步实现 |
|---|---|---|
| 隐藏验收测试通过 | 7/12 | 12/12 |
| 改动的文件数 | 5 | 3 |
| 返工次数 | 3 | 1 |

- 差异原因：直接方式里 Agent 把页码当成从 0 开始，与我心里想的不一致，返工；规格里写明了从 1 开始，一次通过。
- 结论与局限：规格先行在这个功能上表现更好；但只做了一次，功能也比较简单，不能推广到所有情况。

## 任务 7.2：审查、验证与协作安全

- 我的疑点（先于 Agent 完成）：改动的提交信息只写了“update”，看不出做了什么。影响：事后无法追溯，也难以回退。证明：运行 `git log` 查看。处理：要求按步骤提交，信息写明做了什么。
- AI 的补充（采纳）：指出取消订单的接口没有检查订单是否属于当前用户。我核对代码后确认，并补充了一个测试来证明。
- AI 的补充（拒绝）：建议把整个状态流转改写成状态机框架。我拒绝了，因为超出范围，代价大于收益。
- 我的验证闭环：全部测试、依赖规则检查、干净环境启动检查、改动范围检查（只允许改动与功能相关的文件）。我的判断：现有测试并不能发现“越权取消”，所以补充了对应的测试。
- 我的权限清单：允许读取项目文件、运行测试；安装依赖、删除文件、访问网络需要我确认；禁止提交密钥、操作主分支、读取项目之外的文件。每一项都写了理由和风险。
- 我的复盘：直接交给 Agent 适合范围小、规则明确的任务；涉及状态和并发的任务不适合，需要自己先设计。
